## **დეტალები და გადაწყვეტილებები**


### *ბიზნეს ლოგიკა MCP-სგან განცალკევებულია*
`leave_rules.py` და `leave_service.py` MCP-ს არ იყენებენ. ბიზნეს ლოგიკის ყველა წესის შემოწმება Python ფუნქციის გამოძახებით შეიძლება და იგივე ლოგიკა სხვა interface-ითაც შეიძლება გამოვიყენოთ (Web API, CLI) ცვლილებების გარეშე.
`server.py`-ში თითოეული მეთოდი რამდენიმე სტრიქონია: კავშირი, სერვისის ფუნქციის გამოძახება და მისი შედეგის დაბრუნება.

### *თარიღების ფორმატი CSV ფაილებში*
მონაცემების აღწერის მიხედვით თარიღები ISO ფორმატშია, თუმცა `employees.csv` `leave_requests.csv` და `public_holidays.csv` ში არის `M/D/YYYY` ფორმატის თარიღები. ისე გავაკეთე, რომ loader ორივე ფორმატს იღებს, სხვა ნებისმიერ შემთხვევაში აერორებს. **ბაზაში ISO ფორმატს ინახავს**. ISO სტრიქონები ტექსტად სწორად ლაგდება და დარდება (`'2026-02-16' < '2026-11-09'`), რასაც შემდეგ თარიღების დიაპაზონის ფილტრები და შვებულებების გადაფარვის შემოწმებები ეყრდნობა.

### *მონაცემთა ბაზის მთლიანობა*
- CSV ფაილები არასდროს იცვლება და ბაზის მათგან ხელახლა აგება ყოველთვის შეიძლება.
- ყველა ჩანაწერი ერთ ტრანზაქციაში ემატება: ან ყველა მონაცემი იტვირთება, ან არაფერი ინახება.
- `CHECK` შეზღუდვები უარყოფს არასწორ სტატუსებს, წყაროებსა და თარიღების დიაპაზონებს, ხოლო foreign key-ები უცნობ თანამშრომლებსა და შვებულების სახეებს, მაშინაც კი, თუ კოდში შეცდომაა.
- თანამშრომლის ხელმძღვანელი CSV-ში შეიძლება თანამშრომელზე გვიან გვხვდებოდეს, ამიტომ `manager_id`ს foreign key არის `DEFERRABLE INITIALLY DEFERRED` და commit-ის დროს მოწმდება.

### ვალიდაცია სტრუქტურულ შედეგს აბრუნებს
ნებისმიერი სახის პრობლემა არის `Violation`. AI ასისტენტს შეუძლია ახსნას მიზეზი, მიუთითოს მუხლი და შეთავაზოს თუ სად მიმართოს თანამშრომელმა. (როგორც ამას მუხლი 12.3 მოითხოვს)

### HR
შეუძლია თუ არა ასისტენტს შვებულების კონკრეტული სახის შექმნა, განისაზღვრება `leave_types.assistant_supported`-ით, ხოლო HR-თან გადამისამართება  განისაზღვრება `self_service`-ით. თუ HR ამ მნიშვნელობებს შეცვლის, სისტემის ქცევაც შესაბამისად შეიცვლება კოდის შეცვლის გარეშე.

### Output მონაცემებია და არა Exception-ები
როცა MCP exception-ს აგდებს, SDK შეტყობინებას მალავს და კლიენტი მხოლოდ „Error executing tool …“ ხედავს. ამიტომ ისეთი შედეგები როგორიცაა „არასაკმარისი ბალანსი“ ან „მოთხოვნა უკვე გაუქმებულია“ გამოდის `{"ok": false, "errors": [...]}` სახით ახსნასთან ერთად, ხოლო exception-ს მხოლოდ რეალური ბაგები აგდებს. Invalid argument types და missing required arguments თვითონ MCP-ვე უარყოფს.

### User
ჯერ თვითონ MCP სერვერმა არ იცის ვინ იყენებს. `hr_`, ხელსაწყოების აღწერები და სერვერის ინსტრუქციები AI-ს ეუბნება, რომ ეს ფუნქციები თანამშრომლის ასისტენტისთვის არ არის, თუმცა რეალური დაცვა ჰოსტ აპლიკაციის პასუხისმგებლობაა. თანამშრომლის CLI (Task 2) მოდელს `hr_` ხელსაწყოებს არ მიაწვდის და ყოველთვის ავტორიზებული თანამშრომლის ID-ს გამოიყენებს, ამიტომ თანამშრომელი სხვა თანამშრომლის მონაცემებს ვერ ნახავს.

## **დეტალები და გადაწყვეტილებები**


### *დოკუმენტების წაკითხვა და დაყოფა*
DOCX და PDF ფაილები `loaders.py`-ში ერთნაირ ბლოკებად გარდაიქმნება (სათაური, პარაგრაფი, ცხრილი).
`chunking.py` ფაილებს არ ხსნის და მხოლოდ ბლოკებთან მუშაობს: ერთი chunk = ერთი მუხლი (FAQ-ში ერთი კითხვა).
დაყოფა მარტვად გამოვიდა და ასე ყოველი ციტატა ზუსტ მუხლზე მიუთითებს, მაგ. `(HR-POL-02 v4.0, მუხლი 4.4)`. 
სულ 272 chunk-ია. „დოკუმენტის ისტორია“ ცალკე აღინიშნება, რადგან ძველ მნიშვნელობებს გვეუბნება.

### *ჰიბრიდული ძიება*
OpenAI-ის embedding მოდელი ქართულ ტექსტებს ცუდად არჩევს, ძალიან ცუდად. ქართული კითხვა თითქმის ერთნაირ მეტრიკის ქულას იღებს სწორ და სრულიად სხვა, არათემატურ მუხლთან. ამიტომ ძიება ორი ნაწილისგან შედგება:
- **ვექტორული**: ყოველი chunk ერთხელ ითარგმნება ინგლისურად (`cache/`ში ინახება) კითხვაც ითარგმნება და შედარება ინგლისურად ხდება (აზრის მიხედვით ძიება);
- **BM25**: ორიგინალ ქართულ ტექსტში ზუსტი სიტყვებისა და რიცხვების ძიება.
ქართული სიტყვის დაბოლოებები (ბრუნვები, თანდებულები) მარტივი stemmer-ით იჭრება.

შემდეგ ეს ორი სია RRF-ით ერთიანდება. RRF მხოლოდ პოზიციებს იყენებს, ამიტომ კოსინუსისა და BM25-ის სხვადასხვა მაშტაბის ქულების შედარება საჭირო არ არის. თითოეული მეთოდის პირველი 2 შედეგი ყოველთვის რჩება.

### *ძიების ხარისხის გაზომვა*
`eval/retrieval_cases.json`-ში 40 კითხვაა მოსალოდნელი მუხლებით (პირდაპირი, კონფლიქტური, რამდენიმე დოკუმენტზე, დოკუმენტებში არარსებული, ინგლისური). 
**შემთხვევა ითვლება წარმატებულად**, თუ **ყველა** საჭირო მუხლი პირველ k შედეგშია. 
ჰიბრიდული ძიება: hit@6 = 0.97, hit@10 = 1.00. **პასუხისთვის მოდელი 8 chunk-ს იღებს.**

### *წყაროებს შორის კონფლიქტს კოდი წყვეტს*
დოკუმენტები ერთმანეთს ეწინააღმდეგება (მაგ. FAQ: 5 დღით ადრე, პოლიტიკა: 15 დღით ადრე 10-დღიან შვებულებაზე). დოკუმენტები თავად ადგენენ უპირატესობას: **პოლიტიკა > Handbook > FAQ > დოკუმენტის ისტორია.** მოდელი ჯერ აღწერს რას ამბობს თითოეული წყარო და რომელი წყაროები განსხვავდება ერთმანეთისგან (`source_check`), ხოლო ვინ "იგებს", ამას კოდი წყვეტს `registry.py`-ის ავტორიტეტის მიხედვით. ტესტირებისას მოდელი განსხვავებას კარგად ამჩნევდა, მაგრამ უპირატესობას ხშირად არასწორად იყენებდა. 
CLI-ში ჩანს: შენიშვნა, წყაროები და მოძველებული ინფორმაცია (არ გამოიყენება).

### *როცა პასუხი დოკუმენტებში არაა*
მოდელი `found: false`-ს აბრუნებს და ასისტენტი პასუხს არ იგონებს: „ამ კითხვაზე პასუხი კომპანიის პოლიტიკის დოკუმენტებში ვერ მოიძებნა“ და HR-თან მიმართვის რჩევა.

### *უსაფრთხოება კოდშია და არა prompt-ში*
`hr_session.py` (მუხლი 12.3):
- მოდელი მხოლოდ 5 თანამშრომლის ხელსაწყოს ხედავს, `hr_` ხელსაწყოს გამოძახება `PermissionError`ს აგდებს
- თანამშრომლის ID შესვლისას ფიქსირდებ, ამიტომ მოდელს სხვა თანამშრომლის ნაცვლად მოქმედება არ შეუძლია;
- `confirm_leave_request`-ს მოდელი proposal ID-ს ვერ გადასცემს. დადასტურება მხოლოდ თანამშრომლის მომდევნო შეტყობინებაშია შესაძლებელი. მოდელი მოთხოვნას თავისით ვერ დაადასტურებს, თუ თანამშრომელმა არ დაადასტურა, შეთავაზება უქმდება;
- სამომავლო თარიღზე ავადმყოფობის შვებულება მხოლოდ დაგეგმილი სამედიცინო პროცედურისთვისაა შესაძლებელი და ამას კოდი ამოწმებს.

### *შეცდომები*
OpenAI-ის მოთხოვნას 60 წამიანი timeout და 2 განმეორებითი ცდა აქვს. 
API-ს შეცდომები (არასწორი key, ლიმიტი, ინტერნეტი) ქართულ შეტყობინებად გამოდის რჩევასთან ერთად და პროგრამა არ ითიშება. წარუმატებელი შეტყობინება საუბრის ისტორიიდან იშლება. Ctrl+C ით პროგრამა ჩვეულებრივად იხურება.

### *ტესტები OpenAI-ის გარეშე*
ყველა ტესტში OpenAI ჩანაცვლებულია fake ობიექტებით, ხოლო MCP სერვერი in-memory კლიენტით ეშვება დროებით ბაზაზე. 
ტესტებს key და ინტერნეტი არ ჭირდება.

### 1. ინსტალაცია

```powershell
git clone https://github.com/Sula1909/BDO-Task.git
cd BDO-Task
py -m venv .venv
```

თუ PowerShell `Activate.ps1`-ს ბლოკავს: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

```

```

`.env` `.gitignore`-შია და git-ში არ ხვდება. key შეიძლება გარემოს ცვლადადაც მიეთითოს (`$env:OPENAI_API_KEY="sk-..."`).
